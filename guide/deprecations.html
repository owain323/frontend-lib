弃用与移除

删除公开名字必须先登记、迁移窗口有多长、现在有哪些名字在案、以及我们管不住哪些名字

  • docs/DEPRECATIONS.md
  • 规则由 01-tokens/ 实现，判据见文末对应表

一句话：我们删掉任何一个公开名字之前，它必须先在这个文件里出现过。

这不是态度声明，是可以被机器验证的：登记册在 ai/deprecations.json，本文的两个表格由 05-audit/deprecation-doc-gate.py 与登记册双向比对 —— 少写一行、多写一行、版本号写错一个数字，门禁都红。

一 · 你会遇到的两件事#

现象含义你该做什么
某个名字被列进下面的「表 A」它还能用，但有一个明确的消失版本在到那个版本之前换掉，或者钉住版本
某个名字在代码里没了它必须在「表 B」里查得到查不到 ⇒ 我们违约了，请开 issue

「表 B」就是承诺的账本。它的存在本身就是约束：没有登记就不能删。

二 · 迁移窗口有多长#

至少跨一个次版本。

具体说：0.7.x 里标为弃用的名字，最早到 0.8.0 才允许从代码里消失。同一次版本内的修订号不算窗口 —— 本库一天可能发好几个修订号，用「修订号个数」当窗口等于没有窗口。

你看到的它意味着
deprecatedIn: 0.7.7 · removeIn: 0.8.0从 0.7.7 起有替代方案；0.8.0 起原名字会消失
只有 deprecatedIn、没有 removeIn不会发生 —— 登记册要求两个都写，写不出 removeIn 就不许标弃用

⚠️ 诚实边界：我们没有 codemod，也没有运行时告警（组件脚本不打印
console.warn —— 在移动端 WebView 里那是纯噪音）。
所以这个窗口是版本号承诺，不是技术阻断。你能依赖的是
「在这个版本之前它不会消失」，不能依赖「用了会被警告」。

三 · 现在登记在案的#

表 A · 迁窗中（还能用，但有截止版本）#

名字类型弃用于最早移除于替代说明
（无）当前没有名字处于迁移窗口中

这张表是空的，而且它是真的空 —— 不是"还没整理"。
上一个走完流程的名字是 state--delayed，它已经按承诺在 0.8.0 消失，
所以现在躺在表 B 里。

表 B · 已移除#

名字类型移除于替代说明
state--delayedclass0.8.0——这个类承诺了一个"延迟显现"的机制，但全库没有任何 JS 会去设置它依赖的 data-state="shown"，文档也没写。它读起来像本库已经实现了 —— 这类名字最危险：误会发生在读者脑子里，代码不会报错。想要延迟显现，自己给元素加 data-state="shown" 即可。
--measuretoken0.7.4--measure-page / --measure-prose这次移除发生在治理流程建立之前。补登在这里是为了让它不从历史里消失，不是把它洗成"走过流程" —— 那次就是没走。

四 · 我们管得住哪些名字，管不住哪些#

名字分四类进基线。每类的取法都写在 05-audit/deprecation-gate.py 文件头，这里只说你该关心什么：

类型例子抓得到抓不到
token--accent、--sp-3删令牌、改名令牌默认值变化（那不是"名字消失"）
class.btn、btn--ghost、.accordion__item删根类 / 变体 / 槽位类名的样式行为变化
apiSelect、Select.open、AccordionOptions.duration删全局、删成员、删参数对象的字段参数语义变化（同名不同类型）
eventfl-change、fl-select删/改事件名字面量detail 里字段的变化

没进基线的（这是"没做"，不是"量不了"）：

  • data-* 属性名（data-select-btn 这类）。删它同样会让调用方静默失效，但它们现在只被 wiring / api-form 这类接线门禁看着，不在废弃基线里。
  • detail 里的字段、回调选项的语义、CSS 变量的默认值。
  • 组件实例上的私有成员、闭包里的函数。

写这一节的目的不是免责，是把「我们承诺什么」的边界划清楚 ——
上表第四列写「抓不到」的，就是真的抓不到，不要按"应该没问题"理解。

五 · 如果我们要删一个名字，走这五步#

  1. 登记：在 ai/deprecations.json 的 planned 里加一条，写清 deprecatedIn / removeIn / reason。 reason 要回答「为什么它不该继续存在」，不是「我们要重构」。
  2. 给替代：能给就给 replacement。写不出替代方案的名字，多半也不该急着删。
  3. 写进本文的表 A：一行，人读得懂的那种。
  4. 到版本再删：VERSION 推进到 removeIn 之后，才允许从代码里消失。提前删会被判「提前删了」；到期不删会被判「承诺了却没删」。
  5. 挪进表 B：删完把这一行从表 A 移到表 B，保留 removedIn。历史账不销毁 —— 基线（ai/surface.baseline.json）也是只增不减。

reason 写得含糊不算过关，但门禁不判理由对不对，只判它存不存在。这部分靠 review，不假装自动化。

六 · 你自己怎么核#

python 05-audit/deprecation-gate.py            # 登记册与公开面是否自洽
python 05-audit/deprecation-gate.py --selftest # 判据本身抓不抓得到问题
python 05-audit/deprecation-doc-gate.py        # 本文与登记册是否一致

三条都不需要浏览器，秒级返回。

七 · 为什么不索性承诺「0.x 期间一律不删」#

因为那是空话。0.x 按 semver 本来就允许破坏性变更，写一句"绝不破坏" 只会让人以为可以长期依赖，然后在某次 0.8.0 里被打断 —— 比一开始就说清更伤人。

我们的承诺比 semver 严一档、比"绝不破坏"诚实一档：

  • 公开名字的消失，必须先登记、必须跨一个次版本、必须给替代或说明为什么没有；
  • 其余变化（样式、默认值、语义）仍可能在小版本里调整，那部分看 CHANGELOG.md。

到 1.0.0 之后这条政策不变，只是 1.0 之前的破坏性变更会整批在此结清。
