# LESSONS · 门禁与工程的可复用教训

> 这份文件从维护者的内部错误登记里挑出**可以公开、可以复用**的部分。
> 每条都是真实红过的门禁、或真实做错过的事，不是假想。
>
> 为什么不直接公开完整登记：完整版含内部路径、工单代号与排期，
> 那部分不出门。这里保留的是**规则本身** —— 换一个项目也用得上。

## 一、判据的错法（比代码错更难查）

### 1. 作用域取宽了：把"不是它的对象"也抓进来审

**症状** 给表单加了一个"校验中…"的提示，可访问性判据立刻红：
「错误文案太含糊：正在检查是否可用…」。

**根因** 判据本意是"错误文案要说人话"，取数却是「所有被 `aria-describedby`
关联的文本」—— 帮助文字、加载提示全被当成错误文案审。

**规则**
```
写判据前先问：这个选择器圈中的对象，是不是都能按同一标准评价。
圈不干净就缩范围（只取 .field__error / role=alert / aria-invalid 指向的），
不要用"所有 describedby"这种顺手的写法。
```

### 2. 阈值从数据里反推：判的是"短"，不是"含糊"

**症状** 同一条判据里还有一条更隐蔽的：用「长度 ≤ 最长含糊词 + 2」判含糊。
最长词是 `invalid`（7）⇒ 阈值 9 ⇒ 凡是 ≤9 字的文案一律判含糊，
而 20 个字的废话照样过。

**根因** 把长度当成了"含糊"的代理指标，而阈值又是从词表长度推出来的，
两个不相干的量被乘在一起。

**规则**
```
代理指标必须与被判对象有因果关系。判"含糊"就判构成（整句只由含糊词组成），
不要判长度。任何阈值型判据都要配一条反向控制：喂一个真含糊的样本，必须转红。
```

### 3. 参照物取错了一层：拿容器当行宽

**症状** 判"宽通道是否真的越过了正文行长"，量的是宽块与**列容器**的宽度，
得到 420 vs 544，判"没打开"—— 而实际上是打开的。

**根因** 行长只施加在内容块上，列容器是满宽的。两个数不是同一种东西。

**规则**
```
差值型判据先写清"两个数各自是什么"，参照物必须与被判对象同一层
（文本块 vs 文本块，容器 vs 容器）。拿不准就用探针：
同一元素"加类前 / 加类后"各量一次，差值归零才是真的没生效。
```

### 4. 指标名与定义不一致：「未渲染」其实是「文本没被提到」

**症状** 覆盖率门禁把 41 个类记成"未渲染"，逐个去看，其中 10 个每次交互都在渲染。

**根因** 判据是文本匹配，而类名可以由 JS 拼串产生（`'tooltip--' + pos`），
源码里没有完整字面量 ⇒ 渲染了也搜不到。

**规则**
```
指标名必须能被它的实现完整解释；做不到就换名字（"未被文本引用"而不是"未渲染"）。
类名、事件名、storage key 这类字符串契约一律写完整字面量，不拼前缀 ——
拼串的代价不是多打几个字，是所有静态检查都看不见它。
```

### 5. 零文件即通过：判据在没有对象时静默变绿

**症状** 某道扫描类门禁，路径写错导致一个文件都没扫到，结论是 PASS。

**规则**
```
凡是"扫描 / 遍历 / 统计"型判据，必须先断言"扫到了东西"，
再断言"扫到的东西都合格"。零对象一律判失败，不判通过。
```

## 二、删除与清理

### 6. 「清理」不等于「释放空间」

**症状** 某台机器上每次跑完整门禁，回收站就多 2.3 GB；8 轮攒了 16.86 GB。
门禁一直是全绿的。

**根因** 该环境的删除被改写成"移进回收站"（bash 的 `rm` 是个函数、
Python 的 `os.unlink` 被替换）。而回收站与仓库**同一块盘** ⇒
"清理"只是换了目录继续占着，一个字节都没释放。

**规则**
```
① 脚本清理自己创建的临时大目录时，确认删除动作真的删了，
   而不是被平台接管（可以看回收站大小、看卷空闲空间）。
② 「清理」必须度量：跑前跑后各量一次，差值才是证据。
   命令返回 0 只证明调用成功。
③ 用户说"我习惯了"不是验收通过，是问题被默许的信号。
```

### 7. 临时目录的位置会改变测试的语义

**症状** 为了省事，把 `TEMP` 指到仓库内的 `.git/tmp`，结果三道
"模拟无 git 环境"的反向控制全红 —— 它们期望在空目录里只看到一个文件，
却看到了整个仓库的 966 个文件。

**根因** 临时目录在 `.git/` 内部，git 向上就能找到仓库，"这里没有仓库"的前提失效。

**规则**
```
临时目录的边界必须与仓库边界互斥。改全局环境变量（TEMP/TMPDIR/PATH）之前，
先枚举谁会读它 —— 测试代码最常拿这类变量当"干净空间"的锚点。
修一个问题，用最小作用域；不要顺手改跨层的锚点。
```

### 8. 删目录前，先列过它

**症状** 一个临时目录被建到了盘符根下（路径格式错误导致的），发现后直接删了整个目录。
事后无法证明它原本是空的。

**规则**
```
`rm -rf <dir>` 的作用域是整棵子树，而"我知道里面有什么"不等于"我列出过里面有什么"。
删除前先 ls 目标**本身**，并核对"这一层应该只有我刚造的那一个东西"。
拿不出这句话，就不删。
```

## 三、发布与版本

### 9. tag 打在"代码对了"的提交上，但发布门禁看的是 tag 快照

**症状** 功能提交打完 tag 就推，半小时后补的那批视觉基线没跟着走，
发布工作流当场红（页面尺寸变了）。

**根因** 本地的门禁跑的是**工作区**（含未提交的基线），CI 跑的是 **tag 指向的那棵树**。
两者差一个未提交的文件就够红一轮。

**规则**
```
打 tag 前问的是「tag 将要指向的那棵树能过发布门禁吗」，
而不是「我刚跑过的门禁过了吗」。
顺序：先让主干 CI 绿 → 再打 tag → 再推 tag。
```

### 10. 对外文档里的数字，单位必须同量纲

**症状** 更新日志写「16 页有变化（浅色 16 / 暗色 16 / RTL 8）」——
三个数各自都对，但前面说"页"、括号里列"张"，40 张图对应 16 个页面，
读者按字面算不出 16。

**规则**
```
一句话里出现两个以上的数，先确认它们同一个单位；不同单位就分开写。
对外数字必须能被一条命令复算，复算命令记在提交说明里。
已发布的文档不做"偷偷改"—— 改历史条目会让仓库领先于发布物。
```

## 四、这套文档的分层为什么重要

上面十条里，前五条属于**判据的错法**，第六到八条属于**运行时副作用**，
第九、十条属于**发布语义**。它们有一个共同点：

> **都是门禁自己看不见的错。**

代码写错，门禁会红；判据写错、清理没释放空间、tag 指错树 ——
这些是"尺子本身的问题"，而尺子不会量自己。

所以本库的做法是：

- 每条新判据都配一条**反向控制**（注入反例 ⇒ 必须变红），
  证明它有牙，而不是证明它存在；
- 定期做**元检查**：门禁的参照物、作用域、量纲、零对象行为；
- 把每一次"红得没有道理"和"绿得没有道理"都登记下来，变成常驻判据。

这也是 `docs/GUIDANCE.md` 里那条建议的出处：
**判据红的时候，先怀疑判据自己，再怀疑代码。**
