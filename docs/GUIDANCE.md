# GUIDANCE · 建议层

> **这一层的地位**：`docs/INVARIANT.md` 写物理事实，`ai/*.json` 写机器契约，
> 这一份写**工作方式与品味**。它随时可以整份作废 —— 判据是
> INVARIANT 里那句：「如果明天出现一个无限强的模型，这句话还成立吗？」
> 这里的话**不成立**，所以它们必须待在这一层，不许往上渗。

**为什么要有这一层**：把建议混进事实层，会让事实层变成"随时会变的规矩"；
把建议删干净，又会让每次都重新踩同一批坑。分层的意义是 ——
事实层永不变，契约层可协商，建议层可作废。

> ⚠️ **公开面的边界**：这一份只收「工作方式与品味」。
> 发布凭证、账号二次因子、内部排期与到期日**不进这里**，也不进任何公开文档 ——
> 0.11.4 曾因此把四份文档（含本文件）整份移进内部目录。
> 现在的做法是：**只公开可以公开的那一部分**，而不是让三层体系缺一层。

## 一、动手之前

| 建议 | 为什么 |
|---|---|
| 先跑 `python 05-audit/impact-report.py` 看这次改动会波及哪些门禁 | 事后被 20 道门禁同时判红，比事前花 10 秒看影响面贵得多 |
| 改 CSS 前先确认它是不是"生成物"（`dist/` 下的一律是） | 改产物会被 `build-dist --check` 判新鲜度失败，白改 |
| 新增组件前先搜一遍现有组件能不能改 | 44 个组件的维护成本远高于 43 个 |
| 动 `01-tokens/` 之前，先读 `docs/BUDGET.md` 的储备与棘轮 | 令牌层的改动会同时推动体积、对比度、暗色三组判据 |

## 二、写代码

| 建议 | 为什么 |
|---|---|
| 不要写魔法数字：能进令牌的进令牌，进不去的写一行注释说清来历 | 令牌化的价值在于"改一处、全场一致"；散落的数字会把这点吃掉 |
| 组件之间不要 `@import` 互相依赖 | 一旦互相依赖，单独引一个组件就不可能了，包体也会失控 |
| 状态一律走 `data-state`，不要新造状态类 | 类名会被使用者复制粘贴，属性化的状态更容易被脚本和测试读到 |
| 只用逻辑属性（`inline-start` / `block-end`），不写 `left` / `right` | 物理属性是 RTL 的唯一来源；`rtl-render` 门禁会拦住，但改起来比重写便宜得多 |
| 注释写"为什么"，不写"是什么" | 本库注释占比约七成，其中绝大部分是"这个取舍放弃了什么" |
| 加一条门禁时，同时加一条**反向控制** | 见下节 |

## 三、关于门禁

| 建议 | 为什么 |
|---|---|
| 新判据必须配一条"注入反例 ⇒ 必须变红"的自检 | 没有反向控制的判据无法证明自己有牙；仓库里 85 条自检就是为此存在 |
| 判据红的时候，先怀疑**判据自己**，再怀疑代码 | 历史上多次"红得很有道理"其实是参照物取错、作用域取宽、单位取混 |
| 每一条判据都要能回答"它圈中的对象是否都能按同一标准评价" | 圈不干净就会误报；误报比漏报贵，因为它会让人放弃信任门禁 |
| 别用"文本匹配"证明"渲染了" | 类名可以由运行时拼串产生，grep 不到不等于没渲染 |
| 度量型判据必须写清"两个数各自是什么" | 拿列容器当行长、拿字节当体积，都会让判据永远给出同一个结论 |

## 四、AI 协作

| 建议 | 为什么 |
|---|---|
| 让 AI 先读 `llms.txt`，再按需读 `ai/components.json` | 全量读 352 KB 的 CHANGELOG 是浪费上下文 |
| 用 `node ai/cli.js` 校验它产出的契约，而不是相信它说"改好了" | `check` / `diff` / `patch` 三个子命令就是给这件事用的 |
| AI 报告的"已完成"要能被一条命令复核 | 不能复核的完成，等于没完成 |
| 不要让它替你做"要不要发版"这种不可撤回的决定 | 这条是本仓库的惯例，不是技术约束 |

## 五、提交与发布

| 建议 | 为什么 |
|---|---|
| 提交前跑 `npm run gate:fast`，收尾跑 `npm run gate` | `fast` 是纯静态层，秒级；`full` 才是那 9 分钟 |
| 打 tag 之前，先确认**tag 将要指向的那棵树**能过发布门禁 | 本地工作区通过 ≠ tag 快照通过；两者差一个"未提交的基线"就够红一轮 |
| 顺序是：先让 CI 绿 → 再打 tag → 再推 tag | 反过来等于拿发版当试验 |
| 发版失败先查 npm 是否已吃进版本，再决定重试还是回滚 | 有些失败只到 Release 那一步，npm 上其实已经有包了 |
| 移动 tag 之后要重新核对 provenance 里的 `gitCommit` | tag 是发布物与提交之间唯一的锚点，移了就得重新验 |

## 六、什么不该进这一层

- **能机器判定的 → 进契约**（`ai/*.json`），不要写成建议；
- **物理机制的 → 进 `INVARIANT.md`**，不要写成建议；
- **随版本变的数字 → 进 `docs/FACTS.md` 或 `ai/components.json`**，不要手抄进文档。

三层的边界一旦松动，最先坏掉的不是文档，而是**门禁判据的可信度**。

## 附：这一层为什么可以被整份删掉

以上每一条都是"在某个能力水平下、某种协作方式里"的经验。
换成更强的模型、更成熟的团队、更严格的 CI，其中相当一部分会变成多余的动作。
把它们写在这一层，就是为了**将来能干净地删掉它们**，而不必动到事实层和契约层。
