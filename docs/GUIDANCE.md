# 指引（Guidance）

> **这一层是可以整份推翻的。**
> 它记录的是「以当前模型的能力，怎么做最不容易翻车」。
> 模型变强 ⇒ 这一层就该变短。**它变短是好事，不是退步。**

---

## 这一层为什么存在，以及它为什么不该被写死

对照 `INVARIANT.md`：那里写的是**事实**（裸标签选择器的作用域是整个文档），
这里写的是**补丁**（模型看不全全局 ⇒ 让它改之前先跑影响面报告）。

事实不会变。补丁会失效。

所以：

- ❌ 不要把这一层的内容写进门禁——否则三个月后门禁就在拦一个已经不存在的风险，
  而且**没人敢删**（因为"它一直在那儿，删了会不会出事？"）。
- ✅ 这一层应该定期被拿出来问一句：**这条现在还成立吗？**
- ✅ 判断标准很简单：**"如果模型是无限强的，还需要这条吗？"**
  不需要 ⇒ 它随时可以删。

## 一、当前模型下有效的做法

### G-1 改之前先看影响面

```bash
python3 05-audit/impact-report.py
```

**为什么现在需要**：模型倾向于"就改这一处"，看不到它改的文件被谁依赖。

**什么时候可以删**：当模型能在一次上下文里可靠地推导出跨文件依赖时。
（至今还没观察到，所以保留。）

### G-2 一次只改一个语义单元

改完立刻验证，再改下一个。

**为什么现在需要**：连续改 5 处再验证，出错时无法定位是哪一处。
PPT 事故的形态就是"14 页一起改，改完一起崩"。

**什么时候可以删**：当验证本身足够快、且失败定位足够精确时。

### G-3 发现自己在写页面级 override ⇒ 停下来

```css
.slide-3 h1 { ... }   /* ← 这是信号，不是解法 */
```

**为什么现在需要**：模型遇到"改不动"的本能反应是加特异性，而不是改根因。

> ⚠️ 注意：这条的**根因部分**是 `INVARIANT.md` I-2（特异性只增不减），
> 那是事实；"停下来"这个动作是建议。**只有后者属于这一层。**

### G-4 优先改组件，而不是改页面

本库提供组件，不是自由布局。要表达"两栏""卡片网格"，用组件组合。

**为什么现在需要**：模型容易写出 `width: 612px; margin-left: 37px` 这类 magic number。
它们既不能被门禁检查，也不能在暗色模式下自适应。

**什么时候可以删**：当模型默认倾向于复用已有抽象时。

### G-5 贴进 system prompt 的极简版

```
遵守以下编辑边界：
1. 不写裸标签选择器（a{} h1{} button{}）——一律挂组件根类
2. 不新增裸颜色与裸间距——用 tokens
3. 不改 01-tokens/tokens.css，除非任务明确要求改令牌
4. 不写 .page-N .xxx 这类页面级 override 链
5. 改组件样式后必须重跑该组件的视觉基线
6. 改之前先跑 impact-report.py 看影响范围
发现自己在写页面级 override ⇒ 停下来，改组件
```

> 这段是**可替换的**。它是"当前最好用的一段提示词"，不是规范。
> 换模型、换版本 ⇒ 改这段，不需要改任何门禁。

## 二、这一层**不**做的事

| 不做 | 归属 |
|---|---|
| 不定义"哪些组件存在" | `ai/components.json`（Contract） |
| 不定义"strict 档能用什么" | `ai/profiles.json`（Contract） |
| 不断言"裸选择器会污染宿主" | `INVARIANT.md` I-1（事实） |
| 不把上面任何一条接进 `check-all.sh` | —— 门禁只管事实和契约 |

---

## 三、维护规则

1. **每条 G-n 必须写明「什么时候可以删」。** 写不出删除条件的，说明它不是指引，
   要么它其实是 Invariant（搬走），要么它其实什么都没说（删掉）。
2. **每次模型换代，过一遍这一层。** 能删的就删，删不掉的要写清楚为什么还删不掉。
3. **这一层的长度是健康指标。** 它越短，说明模型越强、我们的补丁越少。
   **不要以"这一层写得很全"为荣。**
