# AI 编辑契约

> **这份文件是给「正在修改本库或其使用者页面」的人与 AI 看的操作边界。**
> 不是风格指南，是**硬约束**。违反其中任何一条，库里的门禁会红。

---

## 为什么需要这份文件

一次真实事故：用本库做 14 页 PPT，AI 反复局部修改后整体崩坏，
人工修复 1.5 小时仍未收口。

复盘结论：**问题不在模型不够聪明，而在系统没有划定修改边界。**
库约束了「浏览器里怎么表现」，但没有约束「CSS 能写在哪」——
于是模型可以随手写 `a { color: blue }`，把宿主全站链接改掉。

⇒ 本库能做的不是「保证 AI 不犯错」，是**让 AI 犯的错有上限**。

---

## 一、七条硬约束

| # | 规则 | 为什么 | 门禁 |
|---|---|---|---|
| 1 | **不得写裸标签选择器**（`a {}` `h1 {}` `button {}`） | 作用域是整个文档 ⇒ 会改掉宿主页面所有同名元素 | `bleed-gate.py` |
| 2 | **不得新增裸颜色 / 裸间距** | 一旦绕过令牌，暗色模式立刻失效 | `hardcode-gate.py` |
| 3 | **不得修改 `tokens.css`**（除非任务明确要求改令牌） | 它是全库配色/字号/间距的源头，改它=改整个项目 | `impact-report.py` |
| 4 | **不得新增页面级 override 链**（`.page-3 h1 {...}` 叠加） | 局部改动必须对全局无副作用 | `bleed-gate.py` + 视觉回归 |
| 5 | **组件改动必须重跑该组件的视觉基线** | 行为契约抓不到「样式被改坏」 | `shot-baseline.py` |
| 6 | **组件不得自己造 DOM 事件**（`new CustomEvent` / `createEvent`） | 老 WebView 没有 `CustomEvent` 构造函数 ⇒ 在**用户交互路径上**抛异常，本地测不出来。唯一入口是 `flEmit` | `emit-check.js` 判据 ⑨ |
| 7 | **不得在注释/示例里写不存在的 API**（含 `data-on-*` 这种"属性当回调"） | 用法示例会被照抄；`pg.on(...)` 这种从来没实现过的写法 ⇒ 运行时 `is not a function`。HTML 属性里放不出函数，`data-on-*` 物理上只能是死代码 | `api-form-gate.py` 判据 5 · `emit-check.js` 判据 ⑩ |

> 第 6 条为什么值得单独列：它不是风格问题。
> 自己写 `new CustomEvent(...)` 在 Chrome 里**一切正常**，
> 只在真机上表现为"点了没反应"，而且控制台不一定有线索。
> ⇒ 这类"本地全绿、真机崩"的改动，正是这份契约要挡的东西。
>
> 第 7 条是同一类：**本地全绿、别人照抄就崩**。
> 本库已经有过两次这种事故（`is-*` 状态类、pagination 的 `pg.on`），
> 它们的共同点是"说有、实现里没有"，而没有任何门禁在比对这两者。

## 二、修改之前先看影响范围

```bash
python3 05-audit/impact-report.py           # 我刚改了哪些文件
python3 05-audit/impact-report.py --staged # 只看暂存区
```

它会明确告诉你：

```
🔴 全局影响（必须全量回归）
   01-tokens/tokens.css    令牌层：全库配色/间距/字号的源头
   ⇒ 必须通过：bleed contrast dark-cont visual

🟡 局部影响（只需检查这些）
   03-patterns/content/content.css    组件样式：仅该组件的页面
   ⇒ 需要重跑视觉回归：03-patterns/content/demo.html
```

**不要凭感觉决定要不要跑回归。** 这条命令就是为此存在的。

## 三、局部修改的标准动作

以「改第 3 页的标题」为例：

```bash
# 1. 先看范围
python3 05-audit/impact-report.py

# 2. 只改该页面的文件，不要碰共享层

# 3. 只跑相关的门禁
MODE=fast bash 05-audit/check-all.sh
python3 05-audit/shot-baseline.py --check    # 视觉基线

# 4. 确认没波及别处
python3 05-audit/impact-report.py           # 应当仍然全是局部
```

❌ 反面做法（事故里的实际路径）：

```css
/* 为了修第 3 页 */
h1 { font-size: 31px }          /* 改一个，14 页全变 */
.slide-3 h1 { font-size: 31px } /* 于是开始堆页面级 override */
.slide-4 h1 { font-size: 32px } /* ……一路滑向灾难 */
```

⇒ **正确的修法是改组件，不是改页面。**
如果你发现自己在写 `.slide-N xxx`，停下来 —— 那是信号。

## 四、布局应该用组件，不是自由发挥

本库提供的是**组件**，不是自由布局。
要表达「两栏」「卡片网格」，用现有组件组合，不要自己写宽度。

```html
<!--✅ 用组件组合 -->
<div class="card"><div class="card__body">…</div></div>

<!--❌ 自己发明布局：magic number 谁都维护不了 -->
<div style="width: 612px; margin-left: 37px; transform: translateX(19px)">
```

**理由**：magic number 无法被门禁检查，也无法在暗色模式下自适应。
本库现有的令牌与组件已经覆盖常见场景；找不到合适的场景时，
**加一个组件**比在页面里调数值更省事。

## 五、什么时候该停下来问

以下情况不要自行决定，停下来确认：

- 需要修改 `01-tokens/tokens.css`（影响全局）
- 需要绕过某个门禁（说明门禁要么错了、要么设计要改）
- 一个组件要加第三种视觉变体（先确认能不能用现有变体组合）
- 某个问题「改A 坏了，改 B 也坏了」（可能是耦合，需要先查依赖）

## 六、这套约束的边界（诚实说明）

**本库做不到的事**：

- ❌ 约束使用者在**自己项目**里写的 CSS —— 那些文件不在本库仓库里
- ❌ 替代人工设计判断 —— 布局是否「好看」不是机械判据
- ❌ 保证任何模型不犯错 —— 只能保证它犯的错**有上限、有据可查**

**为什么还要做**：因为「有上限」和「没上限」在真实工作量上是天壤之别。
事故里 1.5 小时修不完，恰恰是因为错误**没有边界**。

## 六·五、这份文档的层次

⚠️ 本节上面的内容是 **Guidance**（建议）。它可以整份推翻，不动门禁。

真正不能被推翻的是另外两层：

| 层 | 在哪 | 怎么改 |
|---|---|---|
| **不变式**（客观事实） | `INVARIANT.md` | 改不了，除非物理定律变了 |
| **契约**（约定） | `ai/*.json` + `API.md` | 发个版本就能改 |
| **建议**（这里） | `GUIDANCE.md` + 本文件 | 随时可整份作废 |

为什么分三层：**约束如果只有一层，今天的约束就是明天的天花板。**
模型变强、做法变化时，放宽的是建议层，不变式一个字都不用动。

⇒ 如果你在写自动化工具，请读 `ai/` 下的机器可读契约，而不是解析这份散文。

## 七、给 AI 的极简版（贴进 system prompt 即可）

```
遵守以下编辑边界：
1. 不写裸标签选择器（a{} h1{} button{}）——一律挂组件根类
2. 不新增裸颜色与裸间距——用 tokens
3. 不改 01-tokens/tokens.css，除非任务明确要求改令牌
4. 不写 .page-N .xxx 这类页面级 override 链
5. 改组件样式后必须重跑该组件的视觉基线
6. 改之前先跑 impact-report.py 看影响范围
7. 状态一律写 data-state 属性，不写状态类名（见 API.md 迁移表）
发现自己在写页面级 override ⇒ 停下来，改组件
```

机器的版本在这里（**优先用它**，不用解析上面的散文）：

- `ai/components.json` / `ai/tokens.json` —— 组件与令牌的结构化事实
- `ai/validate.js` + `node ai/cli.js check <文件>` —— 零依赖校验
- `ai/profiles.json` —— 三档严格程度；`strict` 只允许 `stable` 组件
- `ai/capabilities.json` —— 按**能力**协商可用操作，不按模型名分支
- `ai/behaviors.json` —— **行为覆盖矩阵**：哪些组件必须有哪种微行为
  （状态：`core` 已收编 / `manual` 手写未收编 / `gap` 应做未做 / `n/a` 不适用）
  ⇒ **不登记就红**，不许靠省略跳过；`manual` 与 `gap` 的数量有棘轮，只能降不能升
- **`maturity`（成熟度）是算出来的，不是拍的** —— 每个组件有一个
  `maturity`（`alpha` / `beta` / `stable`）和一份 `maturityReasons`。
  四条判据：有 `demo.html` · 有专属门禁 · 状态全在 `data-*` 属性上（I-8）
  · **行为零欠账**（矩阵里没有 `manual` / `gap`）。
  ⇒ 手写把某个组件改成 `stable` 而它还欠着账，门禁会红（`05-audit/maturity-gate.py`）。
  ⇒ ⚠️ `strict` 档位只放行 `stable`：欠着账的组件在 `strict` 下**不可用**，
     这是有意的 —— 要用就切 `standard`，并接受它们可能还有手写副本。
- `ai/deprecations.json` —— **废弃登记册**：库里曾经有 / 现在有但将来要删的公开名字
  （令牌名 / 类名）。移除公开名字是破坏性变更，必须走流程：
  登记（`deprecatedIn`）→ **跨至少一个次版本**的迁移窗口 → 到 `removeIn` 才允许删。
  判据双向看住（`05-audit/deprecation-gate.py`）：到期没删红、提前删也红。
  ⇒ `ai/surface.baseline.json` 是公开面基线，**只增不减** —— 否则"先删代码再更新基线"
     就能把未登记的移除洗白。

  ⚠️ 诚实边界：我们没有 codemod、也没有运行时告警，所以这个"窗口"只是**版本号承诺**，
     不是技术阻断。要真的拦截，得自己在 CI 里加 lint。
