## 零、为什么必须有第二组

`benchmark/README.md` 里的 T01–T10 测的是**契约层**：Patch 能不能正确应用到组件骨架、
strict 档会不会拒绝 beta、extensions 会不会前向兼容。

它们**回答不了**这个问题：

> 模型用这个库生成出来的**页面**，在真实视口里能不能成立？

一个模型可以完美通过 T01–T10，同时产出一个「393px 横向溢出、暗色下对比度不足、
表格零值印成 `+0.0%`」的页面。**契约合规 ≠ 页面合格。**

## 一、两组的边界（先说清，避免混为一谈）

| 组 | 输入 | 判什么 | 自动评分 |
|---|---|---|---|
| **T01–T10**（契约） | 组件片段 + Patch | 编辑局部性、契约合规 | ✅ 已有 `run.js` |
| **P01–P10**（页面，本文件） | 需求 + 固定示例数据 | 页面能否成立 | ⚠️ **部分**，见判据表 |

**必须遵守的一条**：不得把 T 组的成绩当成页面质量证据，也不得把 P 组的截图当成契约证据。

---

## 二、判据分两类（这条决定了这份文档不是空话）

| 类型 | 含义 | 怎么判 |
|---|---|---|
| **自动** | 能对**任意一个生成出来的 HTML 文件**跑 | `benchmark/score-page.js` |
| **人工** | 只能人对着一张截图/一段交互判，或必须落到仓库内置页才能跑 | 人工记录表 |

⚠️ **一个必须承认的限制**：仓库里 `a11y-ax.js` / `responsive-check.js` / `zoom-reflow.js`
的门禁清单是**硬编码在脚本里的内置页**（`PAGES` 常量、目录名参数），
**不能指向一个模型新生成的文件**。
⇒ 所以「跑一遍全量门禁给生成的页面打分」这条路**不通**，必须另写评分器。
本文件里的「自动」判据，全部由 `benchmark/score-page.js` 实现，不冒充现有门禁。

## 三、十个页面任务（P01–P10）

每个任务给：**需求 → 必须用到的库能力 → 判据 → 参考结果**。
「参考结果」指仓库里已有的、可作为满分样本的页面（评分器自检就靠它）。

| # | 需求（给模型的原话） | 必须用到的能力 | 自动判据 | 参考结果 |
|---|---|---|---|---|
| **P01** | 「用给定数据做一页财务研究报告，含 KPI、趋势、明细表」 | `metric` `delta` `table` `analysis-report` | ① 无横向溢出 ② 无裸颜色 ③ 表格数字符号正确 ④ 用到的类 ≥ 60% 来自本库 | `04-recipes/analysis-report/demo.html` |
| **P02** | 「把这份数据做成学术风格的表格页，含误差列与脚注」 | `table`（`signed-percent` / 缺失值）`longform`（脚注） | ① 同 P01 ③④ ② 缺失值渲染为 `—` 而非 `0` | `04-recipes/table/demo.html` |
| **P03** | 「做一页科学绘图，含误差带与坐标轴标注」 | `09-assets/scientific-plot` | ① 无横向溢出 ② 无裸颜色 ③ 无内联 `<canvas>` 自绘（应走库） | `09-assets/scientific-plot/demo.html` |
| **P04** | 「长文排版，含引用、脚注、目录」 | `longform` + `typography.css` | ① 正文行长 ≤ 75ch ② 无裸字号（`font-size: 14px` 之类） | `04-recipes/longform/README.md` 描述的示例 |
| **P05** | 「两栏：正文 + 侧边说明，窄屏要能折叠」 | `.cmp` / `.cmp--wide-first` / `.cmp--clip` | ① 用了 `.cmp` 而不是自己写 grid ② 393px 单列 ③ 无横向溢出 | `01-tokens/page.css` 的 `.cmp` 定义 |
| **P06** | 「手机优先的窄屏布局，393px 下不能横向滚动」 | `page.css` + `responsive` 约束 | ① 393px `scrollWidth ≤ clientWidth` ② 触控目标 ≥ 44px（量） | 任一 `03-patterns/*/demo.html` |
| **P07** | 「同一页要支持暗色，不许写死颜色」 | `tokens.css` + 容器级主题 | ① 无裸 `#rrggbb` / `rgb()` ② 暗色下 `aria-hidden` 不残留 | `03-patterns/overlay/demo.html` |
| **P08** | 「在**已有页面**上改一处文案，别动别的」 | 局部修改（对应 T01 的页面版） | ① 未修改区域的 DOM 结构 hash 不变 ② 只改目标文本节点 | 任一 demo 页做基线 |
| **P09** | 「表格有 200 行 + 长文本列，要能横向滚动而不是撑破布局」 | `table` + `.table__scroll` | ① 容器 `overflow-x: auto` 生效 ② 页面本身无溢出 | `04-recipes/table/demo.html` |
| **P10** | 「分三轮改：加一列 → 删一行 → 换主题，每轮都别破坏前一轮」 | 多轮局部性 | ① 每轮未修改区 hash 稳定 ② 三轮后无裸颜色 | 无（需现造基线） |

### 为什么「参考结果」这一列很重要

它让评分器**能自检**：拿 `04-recipes/table/demo.html` 去打分，
必须拿到高分；把它故意改坏（注入裸颜色 / 删 `role`），必须掉分。
**没有这一步，评分器自己就是个没牙的门禁**（本项目 E152/E153 的教训）。

## 四、对照实验协议

| 组 | 给模型什么 |
|---|---|
| **A（对照）** | 只有任务原话 + 示例数据。不给本库任何文档 |
| **B（实验）** | 任务原话 + 示例数据 + `README.md` + `ai/START-HERE.md` + `ai assets` 输出 |
| **C（可选）** | 同 B，但显式禁止 beta 组件（strict 语义） |

**必须对齐的变量**：模型与版本、温度、最大输出、工具集、任务顺序（随机化以抵消顺序效应）。
**无法对齐的必须记录**，不能默默忽略。

**重复次数**：每模型每任务 **≥ 20 次**。做不到就在报告里写清样本量与实际能支持的结论强度，
**不得把小样本包装成稳定结论**。

## 五、记录格式

沿用 `benchmark/records.js` 的 `validateRecord` 思路，P 组每条记录至少含：

```json
{
  "group": "P",
  "task": "P01",
  "model": "<模型标识>",
  "modelVersion": "<精确版本>",
  "date": "<ISO 日期>",
  "attempt": 1,
  "params": { "temperature": 0, "maxTokens": 0, "tools": [] },
  "condition": "A|B|C",
  "artifact": "<生成文件相对路径>",
  "score": { "passed": 0, "total": 0, "details": [] },
  "manual": { "reviewed": false, "notes": "" },
  "failures": ["<失败类型>"]
}
```

`score` 必须由 `benchmark/score-page.js` 生成，**不许手工填**——
手填的分数和截图一样，无法复核。

## 六、统计口径

- 报告**分布**，不只报均值：每任务通过率、任务间极差。
- 比率给 **Wilson 95% 置信区间**（小样本下比正态近似可靠）。
- 失败要**分类**（溢出 / 裸颜色 / 符号错 / 未用库 / 结构缺失），不是只报一个数。
- `benchmark/README.md` 里的 95% / 70% 阈值是**待校准的初始决策规则**，
  不是科学阈值。**不得未校准就当成普适标准引用。**

## 七、结论必须回答的六个问题

跑完一轮后，报告必须逐条回答（答不上就是没跑完）：

1. 哪些约束**确实减少**了错误？给出 A/B 差值。
2. 哪些约束**阻止了原本正确的**修改？给出反例。
3. 哪些任务**几乎没有改善**？（说明该任务的约束设计无效）
4. 哪些场景**仍然需要人工**？人工作在哪些环节。
5. 哪些**模型能力变化**会改变结论？（版本升级后需重跑）
6. 本库是否减少了**总修改成本**，而不只是减少了 CSS 错误？
   （要算调用次数、执行时间、人工修复时间）
